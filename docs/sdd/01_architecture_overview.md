# Software Design Document (SDD)
## 01. Architecture Overview and System Context

**Project:** GenesisEmu  
**Version:** 1.0.0  
**Methodologies:** DDD (Domain-Driven Design), TDD (Test-Driven Development), SOLID, Clean Architecture.  

### 1. Purpose
This document outlines the high-level architecture for a Sega Genesis (Mega Drive) emulator. The primary goal is to achieve accurate hardware emulation by modeling the physical components as software domains, while maintaining strict decoupling between the emulation logic and the host operating system (Windows/Linux/WSL).

### 2. Architectural Pattern: Hexagonal Architecture (Ports and Adapters)
To ensure compliance with the **Dependency Inversion Principle (SOLID)** and to facilitate our Dockerized CI/CD and testing environments, the system is designed using a Hexagonal Architecture. 

The system is divided into two strict boundaries:

#### 2.1. The Inner Hexagon: Core Emulation Domain
This layer contains pure emulation logic. It has **zero dependencies** on graphics libraries (like OpenGL or DirectX), audio APIs, or OS-specific file systems. 
*   **Components:** Motorola 68000 CPU, Z80 Coprocessor, VDP (Video Display Processor), YM2612 (Audio), Memory Bus.
*   **Characteristics:** 
    *   Deterministically testable via TDD.
    *   Highly portable (can be compiled as a static/dynamic library).
    *   Exposes internal state via "Ports" (Interfaces).

#### 2.2. The Outer Hexagon: Infrastructure and Adapters
This layer implements the Interfaces (Ports) defined by the Core. It is responsible for interacting with the real world (your PC hardware).
*   **Frontend / Video Adapter:** Reads the pixel buffer generated by the VDP Core and renders it to the screen (e.g., using SDL2, Raylib, or OpenGL).
*   **Audio Adapter:** Pushes the audio samples generated by the YM2612 Core to the host audio device.
*   **Input Adapter:** Captures host keyboard/gamepad events and translates them into the DE-9 I/O port format.
*   **ROM Loader Adapter:** Reads the `.md` or `.bin` ROM file from the host filesystem and injects it into the Core's cartridge memory space.

### 3. Environment & Deployment Strategy (WSL2 + Docker)
Given the host environment (Windows 10, WSL2, GTX 1060 6GB), the emulator workflow is divided to maximize developer experience and runtime performance.

*   **Development & Testing (Dockerized):**
    *   The Core Emulation Domain is fully containerized.
    *   Compilers (GCC/Clang or equivalent), Build Systems (CMake/Make), and Test Runners (GoogleTest, Catch2, etc.) reside inside the Docker image.
    *   TDD cycles (compiling and running unit tests for CPU opcodes, Bus routing, VDP state) are executed seamlessly inside the container.
*   **Execution & Rendering (Native / WSLg):**
    *   Real-time AV rendering (60 FPS, low latency audio) from inside a Docker container to a Windows host introduces significant overhead and timing issues.
    *   **Solution:** The Frontend Adapter will be compiled and executed directly on WSL2 (using WSLg for Wayland/X11 rendering) or natively on Windows, linking dynamically to the Core library built by the Docker container. The GTX 1060 will easily handle any VSync or Shader requirements at the outer layer.

### 4. Domain-Driven Design (DDD) Approach
The physical hardware of the Sega Genesis dictates our Domain.
*   **Ubiquitous Language:** Terminology such as `VdpCtrl`, `VBlank`, `DMA`, `Word`, `Longword`, and `ROM Header` will be strictly enforced in the codebase and documentation to match the official hardware specifications.
*   **Aggregates:** The system is composed of hardware aggregates (e.g., the `VDP` is an aggregate root that contains `CRAM`, `VRAM`, and `VSRAM`).
*   **Communication:** Components do not communicate directly. They communicate exclusively through the `MainBus` (Memory Map), exactly as the physical hardware relies on electrical traces on the motherboard.

### 5. TDD Strategy overview
Every hardware component will be developed following the Red-Green-Refactor cycle.
1.  **Red:** Write a test based on the technical specification (e.g., "Writing `$8010` to `$C00004` enables HBlank Interrupt in VDP").
2.  **Green:** Implement the minimum logic in the VDP register state machine to pass the test.
3.  **Refactor:** Optimize bitwise operations and memory footprint without breaking the tests.

# Software Design Document (SDD)
## 08. Infrastructure, Adapters, and Docker Strategy

**Project:** GenesisEmu  
**Version:** 1.0.0  

### 1. Purpose
This document defines the **Outer Hexagon** (Infrastructure Layer) and the DevOps strategy. It explains how the pure, hardware-agnostic Core Domain interacts with the Host Operating System (Windows 10 / WSL2) and how Docker is utilized to maintain a clean development environment without introducing rendering or audio latency.

### 2. The Outer Hexagon (Adapters)
Following the Ports and Adapters architecture, the Core Domain does not know about screens, speakers, or keyboards. The Host implements Adapters to translate Core data into physical stimuli.

#### 2.1. Video Adapter (GPU Rendering)
*   **Responsibility:** Reads the pixel buffer generated by the VDP Core and presents it to the monitor.
*   **Implementation:** A library like SDL2, Raylib, or OpenGL.
*   **Hardware Utilization (GTX 1060):** The native resolution of the Genesis is tiny (e.g., 320x224). The Core will output a raw array of RGB values. The Video Adapter will upload this array to the GTX 1060 as a Texture. The GPU will handle upscaling, VSync, and post-processing (e.g., CRT Shaders), resulting in 0% strain on the CPU.

#### 2.2. Audio Adapter
*   **Responsibility:** Pulls PCM sample buffers from the Z80/YM2612 subsystem and pushes them to the Host sound card.
*   **Constraint:** Audio requires extreme low latency. The Adapter will use a ring buffer and request samples at a fixed rate (e.g., 44100 Hz, 16-bit stereo).

#### 2.3. Input Adapter (I/O Ports)
*   **Responsibility:** Translates Host keyboard presses or Gamepad inputs (XInput/DirectInput) into the Sega DE-9 pinout format.
*   **Logic:** If the user presses the 'A' button on their controller, the Adapter pulls the corresponding bit LOW (0) on the memory address mapped to the `MainBus` I/O Port (`$A10003`).

### 3. Docker & WSL2 Strategy (The "Build Container" Pattern)
Running a high-performance 60FPS graphical application with real-time audio *directly inside* a standard Docker container and piping it through WSL to Windows creates unacceptable latency and audio tearing.

To solve this, we will use Docker strictly as a **Build and Test Environment**.

#### 3.1. The Docker Container (Toolchain)
A `Dockerfile` will define the exact compiler (GCC/Clang), build system (CMake/Make), and testing frameworks (e.g., GoogleTest).
*   **TDD Workflow:** You write a test. You run `docker compose up test`. The container boots, compiles the Core, runs the unit tests, prints the result, and exits. 
*   **Zero Dependencies on Host:** Your Windows/WSL installation will not need any C++ compilers or libraries installed. Everything is containerized.

#### 3.2. Execution and Rendering (Native Binary)
When you want to actually *play* a game:
1.  The Docker container acts as a compiler. It mounts your source code volume, compiles the `GenesisEmu` executable, and outputs the binary into a `/build` folder shared with WSL.
2.  You execute this compiled binary **natively in WSL2** (using WSLg for Wayland/X11 graphics hardware acceleration) or cross-compile it for Windows native execution.
3.  This guarantees direct access to your GTX 1060 and host audio drivers, ensuring perfect synchronization.

### 4. Folder Structure (Clean Architecture)
To enforce these boundaries, the repository will be structured as follows:

```text
/GenesisEmu
 ├── /docs                 # SDD, UML, and hardware specs
 ├── /docker               # Dockerfiles and docker-compose.yml
 ├── /src
 │    ├── /Core            # The Inner Hexagon (M68k, VDP, Bus, Z80). NO SDL/OpenGL here.
 │    ├── /Adapters        # The Outer Hexagon (SdlVideoAdapter, SdlAudioAdapter).
 │    └── /App             # Entry point (main), wires Core to Adapters.
 ├── /tests
 │    ├── /CoreTests       # TDD unit tests for the Core Domain (run via Docker).
 │    └── /Integration     # Tests for Adapters.
 └── CMakeLists.txt        # Build instructions
```

### 5. Final Architecture Flow
1. Host User runs `GenesisEmu`.
2. `App` instantiates `SdlVideoAdapter`, `MainBus`, `M68k`, `VDP`.
3. `App` loads `sonic.md` via `RomLoaderAdapter` into `Cartridge` entity.
4. `App` attaches `Cartridge` to `MainBus`.
5. `App` starts the `EmulateFrame()` loop.
6. `M68k` fetches opcodes from `MainBus`, processes logic.
7. `VDP` generates pixels, passes them to `SdlVideoAdapter`.
8. Frame is rendered on the GTX 1060.
